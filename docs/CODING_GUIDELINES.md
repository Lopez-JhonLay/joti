# Joti — Coding Guidelines

## 1. Purpose

This document establishes coding standards and best practices for Joti.

All implementations must follow these guidelines alongside `PRD.md`.

### Core Principles

- Prioritize simplicity, readability, and maintainability.
- Follow existing project patterns and conventions.
- Write secure, type-safe, and testable code.
- Prefer built-in framework capabilities over unnecessary dependencies.
- Avoid premature abstractions and overengineering.
- Keep UI, business logic, and data access responsibilities clear.

## 3. Project Structure

Use file-type-based organization with logical subfolders.

```text
app/
  (auth)/
  (tabs)/
  _layout.tsx

components/
  ui/
  journal/
  companies/
  projects/

hooks/
lib/
constants/
types/
assets/

convex/
  schema.ts
  auth.ts
  companies.ts
  projects.ts
  entries.ts
  attachments.ts
  lib/
```

### Rules

- Keep `app/` focused on routing and screen composition.
- Place reusable UI components in `components/`.
- Group related components into meaningful subfolders.
- Keep reusable React hooks in `hooks/`.
- Keep shared utilities in `lib/`.
- Keep backend logic inside `convex/`.
- Avoid unnecessary service or repository layers.
- Do not introduce new folders without a clear responsibility.

## 4. Naming Conventions

| Element            | Convention       | Example          |
| ------------------ | ---------------- | ---------------- |
| Files              | kebab-case       | `entry-form.tsx` |
| Components         | PascalCase       | `EntryForm`      |
| Functions          | camelCase        | `createEntry`    |
| Variables          | camelCase        | `companyId`      |
| Hooks              | use + camelCase  | `useEntryDraft`  |
| Types / Interfaces | PascalCase       | `JournalEntry`   |
| Constants          | UPPER_SNAKE_CASE | `MAX_FILE_SIZE`  |
| Convex tables      | plural camelCase | `companies`      |

### Rules

- Use descriptive, meaningful names.
- Avoid unclear abbreviations.
- Prefer named exports for reusable modules.
- Use default exports where required by Expo Router.
- Follow Expo Router's required filenames and route conventions.

---

## 5. TypeScript Standards

- Enable TypeScript strict mode.
- Avoid `any`; prefer `unknown` when types are uncertain.
- Use generated Convex types, including `Id<"table">`.
- Define explicit types at important module boundaries.
- Prefer type inference for simple local variables.
- Use union types for fixed statuses and categories.
- Handle nullable and optional values explicitly.
- Avoid unnecessary type assertions and non-null assertions.
- Never silence TypeScript errors without a justified reason.

Do not duplicate types already generated by Convex.

---

## 6. React Native & Expo

### Components

- Use functional components and React hooks.
- Keep components focused on one responsibility.
- Extract reusable components when duplication or complexity justifies it.
- Keep screen-specific components local when appropriate.
- Prefer composition over deeply nested conditional rendering.
- Avoid unnecessary effects and derived state.

### Navigation

- Use Expo Router.
- Group authentication and main application routes logically.
- Keep navigation logic separate from business logic.
- Use route protection for authenticated screens.
- Handle loading and authentication transitions correctly.
- Do not rely on route protection for backend authorization.

### State Management

Use:

- Convex hooks for reactive server data.
- React state for local component state.
- React Context for genuinely shared client state.
- React Hook Form for form state.

Avoid introducing Zustand, Redux, or TanStack Query without a demonstrated requirement.

---

## 7. NativeWind & Styling

Use NativeWind as the primary styling solution.

### Rules

- Use centralized semantic design tokens.
- Support light and dark themes.
- Avoid hardcoded colors throughout components.
- Reuse spacing, typography, and radius conventions.
- Keep styling readable and consistent.
- Use responsive utilities where appropriate.
- Use React Native StyleSheet only when NativeWind is insufficient or impractical.
- Respect safe areas, keyboard behavior, and Android screen sizes.
- Maintain accessible contrast and touch targets.

### Design References

UI implementation must follow approved reference images and mockups for:

- Layout and visual hierarchy.
- Light and dark color tokens.
- Typography and spacing.
- Component behavior.
- Responsive layouts.

Do not invent an unrelated visual design system.

---

## 8. Forms & Validation

Use React Hook Form with Zod for client-side form handling.

### Rules

- Define reusable validation schemas.
- Show clear, field-specific validation errors.
- Validate completed entries separately from incomplete drafts.
- Support the three-step guided journal form.
- Preserve entered values when navigating between steps.
- Keep optional fields genuinely optional.
- Prevent accidental duplicate submissions.
- Avoid unnecessary re-renders during form updates.

### Backend Validation

Convex must independently validate submitted arguments and enforce business rules.

Client-side validation improves UX but must never be treated as a security boundary.

---

## 9. Convex Backend Architecture

Organize backend functions by domain.

Examples:

- `companies.ts`
- `projects.ts`
- `entries.ts`
- `attachments.ts`

### Rules

- Use queries for reading data.
- Use mutations for database writes.
- Use actions for operations requiring external or unsupported mutation/query APIs.
- Prefer mutations for transactional state changes.
- Keep public Convex functions focused and understandable.
- Extract shared business logic only when reused or sufficiently complex.
- Keep internal helpers and internal functions inaccessible as public APIs.
- Avoid unnecessary controllers, services, or repositories.
- Use explicit argument validators for exposed backend functions.

Never trust identifiers or ownership information supplied by the client.

---

## 10. Authentication & Authorization

Use Convex Auth with Google OAuth as defined in the PRD.

### Rules

- Require authentication for protected operations.
- Resolve the authenticated user's identity on the server.
- Centralize reusable authentication and ownership checks.
- Verify ownership before reading or modifying private records.
- Validate relationships between companies, projects, entries, and attachments.
- Reject cross-user access, including manipulated document IDs.
- Enforce session expiration according to the PRD.
- Never rely solely on frontend checks for security.

Authentication establishes identity; authorization determines which records that identity may access.

---

## 11. Database & Queries

### Schema

- Define tables and validators in `convex/schema.ts`.
- Use native Convex document IDs.
- Use appropriate optional fields and union types.
- Validate relationships before writing records.
- Maintain consistent timestamps and record statuses.
- Store user ownership information where required.

### Query Performance

- Use indexes based on actual query patterns.
- Prefer indexed queries over unnecessary full-table scans.
- Use pagination for potentially large datasets.
- Apply appropriate server-side filtering.
- Keep query results limited to required data.
- Use Convex search indexes when full-text search is needed.
- Avoid unnecessary database indexes.

### Data Integrity

- Prevent entries from referencing another user's company or project.
- Prevent entries from referencing projects belonging to a different company.
- Respect archived and deleted record states.
- Enforce deletion and restoration rules consistently.

---

## 12. Autosave & Draft Management

Autosave is a core reliability requirement.

### Rules

- Use debounced updates to reduce unnecessary writes.
- Persist only changed fields where practical.
- Preserve draft state between form steps.
- Display Saving, Saved, and Save Failed states.
- Provide a manual Retry action.
- Warn before leaving with unsaved changes.
- Never display an unsuccessful save as successful.
- Avoid unnecessary writes for unchanged values.

### Concurrency Protection

- Use server-checked revision numbers or equivalent optimistic concurrency control.
- Reject stale updates that would overwrite newer data.
- Handle conflicts without silently discarding user changes.
- Ensure entry completion validates the latest saved content.

Full offline synchronization is outside the MVP scope.

---

## 13. File Storage

Use Convex File Storage for image attachments.

### Rules

- Accept supported image formats only.
- Enforce the 5 MB maximum file size.
- Validate file metadata and content where practical.
- Authorize uploads and attachment association.
- Verify ownership of associated journal entries.
- Protect private file access through an authorized delivery mechanism.
- Do not treat possession of a storage URL as proof of authorization.
- Prevent attachments from being associated with unauthorized records.
- Track and remove orphaned uploads.
- Preserve attachments during the Trash recovery period.
- Delete associated files after permanent entry deletion.

Do not expose private company evidence through unrestricted file sharing.

---

## 14. Error Handling

Use consistent, minimal application error conventions.

### Rules

- Handle expected errors explicitly.
- Provide user-friendly error messages.
- Distinguish validation, authentication, authorization, and conflict errors.
- Avoid exposing stack traces or internal details to users.
- Do not silently swallow exceptions.
- Provide actionable recovery options where appropriate.
- Keep logging minimal and free of sensitive journal content.

Avoid implementing a large custom error framework.

---

## 15. Security & Privacy

Security requirements apply to both frontend and backend code.

### Rules

- Validate all untrusted inputs.
- Enforce backend authorization.
- Prevent unauthorized record access.
- Protect private attachment access.
- Avoid logging secrets, credentials, or sensitive journal text.
- Use platform-appropriate secure storage for authentication tokens.
- Avoid storing sensitive user content in insecure device storage.
- Handle session expiration securely.
- Protect exported files from unintended disclosure.
- Escape spreadsheet formula-like values in CSV exports.
- Display privacy reminders before attaching potentially confidential work evidence.

Never assume that an authenticated user can access every record in the database.

## 16. Testing Standards

Use a balanced testing strategy.

### Unit Tests

Test important pure logic, including:

- Validation rules.
- Impact status handling.
- Draft state transitions.
- Utility functions.
- CSV formatting and escaping.

### Backend Tests

Test:

- Authentication requirements.
- Record ownership.
- Cross-user access denial.
- Company and project relationships.
- Entry creation and updates.
- Stale autosave protection.
- Attachment authorization.
- Trash and restoration.

### Critical Flow Tests

Cover:

- Google authentication.
- Creating and completing entries.
- Saving and resuming drafts.
- Autosave failure and retry.
- Searching and filtering.
- Uploading attachments.
- Restoring deleted entries.
- Exporting work history.

Use testing tools compatible with the selected Expo and Convex versions.

Prioritize meaningful coverage over arbitrary coverage percentages.

## 17. Linting & Formatting

Use ESLint and Prettier.

### Rules

- Maintain consistent formatting.
- Follow supported Expo ESLint configuration.
- Include React and React Hooks lint rules.
- Apply appropriate TypeScript lint rules.
- Avoid conflicting formatter configurations.
- Keep formatting rules centralized.
- Do not disable lint rules without justification.
- Keep generated files excluded where appropriate.

Use available project scripts for linting, formatting, and type checking.

---

## 18. Dependencies

- Use one package manager and one lockfile.
- Install Expo-managed packages using compatible versions.
- Verify React Native and NativeWind compatibility.
- Prefer maintained, established libraries.
- Avoid dependencies that duplicate existing framework capabilities.
- Avoid premature abstraction libraries.
- Keep development and runtime dependencies appropriately separated.

---

## 19. Git Conventions

Use a simple Git workflow.

### Branching

- `main` represents the stable working branch.
- Use small feature or fix branches when appropriate.
- Keep changes focused on a specific task.

### Commit Messages

Use clear, descriptive commit messages.

Examples:

- `feat: add company management`
- `fix: prevent stale autosave updates`
- `refactor: extract entry validation`
- `test: add entry authorization tests`
- `docs: update coding guidelines`

Prefer small, logically grouped commits.

---

## 20. Documentation & Comments

### Rules

- Write self-explanatory code.
- Use comments to explain why something exists, not restate what it does.
- Document non-obvious business rules.
- Explain important security and concurrency decisions.
- Avoid unnecessary comments and excessive documentation.
- Update relevant documentation when implementation contracts change.

Keep the following responsibilities separate:

- `PRD.md` — Product requirements and scope.
- `CODING_GUIDELINES.md` — Coding standards and technical conventions.
- `AGENTS.md` — AI agent workflow and behavioral instructions.
- `TASKS.md` — Implementation phases and task progress.

---

## 21. Definition of Code Quality

Joti's code should be:

1. **Readable** — Easy to understand without excessive explanation.
2. **Maintainable** — Simple to update without introducing regressions.
3. **Secure** — Private data protected through backend authorization.
4. **Type-safe** — Explicit boundaries and minimal unsafe operations.
5. **Reliable** — Predictable behavior during failures and concurrency.
6. **Testable** — Important business logic can be verified independently.
7. **Consistent** — Follows the established project conventions.

**Guiding Principle:**

> Write the simplest correct solution that meets the requirements, protects user data, and remains easy to maintain.
